# Semi-Self-Signup Section

Kahoot-style self-signup: a study admin enables self-signup for a study and gets back a short 5-letter
code. Anyone who scans a QR code or types the code in gets their own anonymous account, deployment, and
participant created on the spot, with the magic link handed back directly so their device can redirect
immediately - no CSV export, no polling.

**Disabled by default.** A study must be explicitly opted in via the admin endpoint below.

## 1. Admin: Enable, Reconfigure, End

**Purpose**: Lets a study admin (`canManageStudy`/`canLimitedManageStudy`) turn self-signup on for a study,
change its participant cap or role, and turn it off again.

- `PUT /api/studies/{study-id}/self-signup` - enable (first call) or reconfigure (later calls). Body:
  `maxParticipants`, `participantRoleName`, `clientId`, `redirectUri`, `subdomain?`, `expirationSeconds?`.
  The study must be live and `participantRoleName` must exist on its protocol. This is **re-checked at every
  signup**, not just here: if the protocol is later edited/replaced without disabling self-signup first,
  dropping the configured role, a signup attempt fails fast with `409` (reservation released immediately)
  instead of creating an orphaned Keycloak account before discovering the mismatch.
- `GET /api/studies/{study-id}/self-signup` - current config/status (short code, enabled, cap, current
  count), or `null` if never enabled. Useful for an admin UI to render the code/QR and progress.
- `DELETE /api/studies/{study-id}/self-signup` - ends self-signup (`enabled = false`). The short code and
  cumulative participant count are **kept**, not reset - re-enabling later resumes under the same code, so
  a previously printed/scanned QR code keeps working.

**The short code**: 5 uppercase letters, excluding `I`, `O`, and `Q` (visually ambiguous at small sizes -
easily confused with `1`/`0`/each other). Generated once on first enable and never regenerated by later
calls. Lookup is case-insensitive (the public endpoint normalizes with trim + uppercase).

**`maxParticipants` is a lifetime cap**, not reset by end/re-enable - it represents "this many people may
ever join via this code." It may be raised or lowered on a later `PUT` call.

## 2. Public: Sign Up by Code

**Purpose**: The only mutating, unauthenticated endpoint in this codebase - anyone with the code can create
their own account without logging in.

- `POST /api/self-signup/{short-code}` - creates one new anonymous account/deployment/participant for the
  code's study and returns `{ "magicLink": "..." }` to redirect to. No request body.
- Deliberately `POST`, not `GET`: a browser reload/prefetch on a `GET` would silently mint a second
  account. The QR/link a participant scans should point at a small landing page that issues this `POST`
  client-side and then redirects to the returned magic link - that landing page is not part of this
  backend.

**Failure responses**:

| Status | Meaning |
|---|---|
| 404 | Unknown short code |
| 409 | Self-signup is disabled, the study's participant cap has been reached, or the study's protocol no longer defines the configured participant role |
| 429 | Too many requests from the caller's IP address (see rate limiting below) |

Every one of these is an **expected** outcome of normal use against a public, unauthenticated endpoint - a
typo, a full study, a stale role after a protocol edit, or rate limiting - rather than an application error,
so none of them page the client-errors notification channel (`ResourceNotFoundException.quiet` /
`ConflictException.quiet`; the `429` handler skips it unconditionally). Only a genuinely unhandled failure
(e.g. an uncaught exception) still notifies - an attacker guessing codes or hammering the endpoint at its
documented limits must not be able to flood that channel just by doing what the endpoint already rejects.

### Concurrency: many people signing up at once

Capacity is claimed in two phases, via `SelfSignupReservationStore` (table `self_signup_reservation`):

1. **Claim, before Keycloak.** Locks `study_self_signup`'s row, counts its confirmed
   `current_participant_count` plus this study's still-live (non-expired) reservations, and - only if
   under `maxParticipants` and enabled - inserts a reservation that expires after
   `self-signup.reservation.ttl-seconds` (default 300s) and returns its id. Postgres's row lock serializes
   concurrent claims for the same study, so a burst of simultaneous signups gets *exactly* `maxParticipants`
   successful claims; everyone else is rejected with `409` immediately - **before any Keycloak account is
   created for them**. Checking capacity only after minting an account would waste one for every caller
   beyond the cap under a burst, and - since the anonymous-account cleanup sweep is disabled by default -
   those wasted accounts would otherwise sit in Keycloak indefinitely.
2. **Finalize, with the participant.** Locks `study_self_signup`'s row FIRST - the same order as the claim
   step above, not incidentally - before touching the reservation at all. Only then, once Keycloak succeeds,
   is the reservation converted into a confirmed slot (deleted, with `current_participant_count`
   incremented) inside the SAME transaction that persists the participant/deployment rows (see
   `AnonymousServiceImp.addParticipantsAndGroupsCore`'s `beforeCommit`). Locking first matters: a
   reservation right at its expiry instant would otherwise briefly be counted by neither query - excluded
   from the claim step's live-reservation count (already past `expires_at`) yet not reflected in
   `current_participant_count` either (not bumped until finalize's later statement) - letting a concurrent
   claim slip into that gap and oversell the cap by one. Locking up front closes it: any concurrent claim
   for the same study now either fully precedes this finalize or fully blocks behind it. A crash or thrown
   exception anywhere in the transaction rolls both writes back together.

   **Trade-off**: because the lock is held for the whole persistence transaction, a claim for the same study
   now queues behind whichever signup is currently persisting, not just behind finalize's own two
   statements - correctness over raw throughput during a burst. Decoupling them to improve throughput would
   let a downstream persistence failure permanently burn a capacity slot with no participant and nothing for
   `SelfSignupReservationCleanupJob` to reconcile it against, so this is intentional.

A reservation is a **hold, not a commitment**: unless something releases it early (a failure known to have
happened BEFORE Keycloak was ever contacted - see Orphaned accounts below), it simply expires if never
finalized - claim/finalize only ever count live (`expires_at > now()`) reservations, so an interrupted
request can never permanently consume capacity.

Unlike the rate-limit sweep below, `SelfSignupReservationCleanupJob` (`self-signup.reservation.cleanup-cron`,
default every 5 minutes) is **not** mere table hygiene. An expired, never-finalized reservation is the only
remaining evidence that a signup attempt was made and *may* have created a Keycloak account this process
never got to record anywhere - e.g. the process crashed, the Keycloak call timed out, or its response was
lost after Keycloak had already processed it. Every study id an expiry sweep finds is reconciled into the
existing anonymous-account cleanup ledger (`recordCleanupSchedule`, same as [ws-exports.md](ws-exports.md))
*before* the reservation row is deleted. This is deliberately defensive: it costs nothing if no such account
actually exists (a later sweep just finds nothing to delete), but skipping it risks leaving a real orphan
with no trace at all.

The account/deployment/participant creation itself follows the same load-bearing convention as the
existing bulk anonymous-account pipeline (see [ws-exports.md](ws-exports.md)): participant id, participant
group id, study deployment id, and Keycloak account id are all the **same UUID**, because Keycloak's
`inDeployment` attribute (stamped by the bulk-users extension) becomes the JWT `in_deployment` claim that
authorization checks against. This is why signup always goes through the bulk account-creation call (even
for a single account) rather than the older single-account path, which doesn't stamp that attribute.

### Rate limiting

Basic per-IP throttling (`self-signup.rate-limit.per-ip-per-minute`, default 20/minute) guards against a
single client hammering the endpoint - it does not affect a room full of people signing up from distinct
IPs. Implemented as fixed 1-minute windows in the `self_signup_rate_limit` table (Postgres-backed rather
than in-memory, since the app sits behind a reverse proxy and an in-memory counter would not be safe if the
app is ever run as multiple instances). A daily-configurable scheduled job
(`SelfSignupRateLimitCleanupJob`, `self-signup.rate-limit.retention-hours` / `cleanup-cron`) sweeps windows
older than the retention horizon so the table doesn't grow unbounded.

### Orphaned accounts

The two-phase reservation above prevents *over-capacity* callers from ever reaching Keycloak, but an
account can still be orphaned within the allowed capacity - e.g. Keycloak succeeds but the subsequent
deployment/participant transaction fails, or the Keycloak call itself throws (a timeout or a lost response
can follow a call Keycloak actually completed server-side, so a thrown exception is never proof no account
was created).

Once Keycloak has been called, `SelfSignupPublicServiceImpl` deliberately does **not** delete the
reservation on failure - only `finalize()` (participant persistence succeeding) ever removes it from that
code path. This is intentional: the reservation is the only durable evidence a signup attempt happened, and
deleting it eagerly on a merely-possible failure would destroy that evidence before
`SelfSignupReservationCleanupJob`'s reconciliation ever gets a chance to use it. An unfinalized reservation
is instead left alone to expire and go through that job's record-then-delete reconciliation (see above).

Even a **successful** signup needs care here: the cleanup schedule for its account is written inside the
same transaction as `finalize()` and the participant persistence, via `AnonymousAccountCleanupStore.upsert`
called directly (not `AnonymousService.recordCleanupSchedule`, which catches and swallows write failures -
correct for its normal callers, but not here). If that write failed silently instead, participant
persistence could still succeed, the reservation would still be deleted, and the request would still
return success - leaving a real, working account with *no* cleanup-ledger row and no reservation left to
reconcile it later. Doing it inside the transaction means a failed write rolls back the whole thing
instead: the reservation survives intact, and `SelfSignupReservationCleanupJob`'s own non-swallowing write
(see above) picks it up once it expires. Only the paths that never reach that transaction at all (e.g. a
malformed Keycloak response) fall back to the best-effort `AnonymousService.recordCleanupSchedule` call -
safe there specifically because the reservation is never finalized on those paths either, so the
reconciliation job remains the backstop regardless of whether that particular attempt succeeds.

See [ws-exports.md](ws-exports.md) for how the ledger's cleanup sweep itself works; none of this deletes an
orphaned account outright (no account-deletion-on-failure path exists in this codebase) - it just ensures
the orphan isn't invisible to that sweep.

One trade-off worth knowing: because nothing releases a reservation early anymore, a burst of failures
that are *actually* harmless (e.g. Keycloak is briefly down and every call fails fast and unambiguously)
still holds those slots for the full `self-signup.reservation.ttl-seconds` before they free up - a study
can appear temporarily fuller than it really is for up to that long during an outage. This is accepted as
the safer default: a temporary, self-healing reduction in available capacity is preferable to a permanently
untracked orphaned account.

## Configuration

| Property | Env var | Default | Meaning |
|---|---|---|---|
| `self-signup.rate-limit.per-ip-per-minute` | `SELF_SIGNUP_RATE_LIMIT_PER_IP_PER_MINUTE` | `20` | Per-IP requests/minute before `429` |
| `self-signup.rate-limit.retention-hours` | `SELF_SIGNUP_RATE_LIMIT_RETENTION_HOURS` | `1` | How long a rate-limit window is kept before cleanup |
| `self-signup.rate-limit.cleanup-cron` | `SELF_SIGNUP_RATE_LIMIT_CLEANUP_CRON` | `0 0 * * * ?` | Cron schedule for the rate-limit table sweep |
| `self-signup.reservation.ttl-seconds` | `SELF_SIGNUP_RESERVATION_TTL_SECONDS` | `300` | How long a claimed capacity reservation holds a slot before it expires |
| `self-signup.reservation.cleanup-cron` | `SELF_SIGNUP_RESERVATION_CLEANUP_CRON` | `0 */5 * * * ?` | Cron schedule for the expired-reservation sweep |
